# engram sync protocol — v1

Spec for the offline-first synchronization between the Android client and
`engram-server`. This is the contract the M1/M2 issues implement; the pre-written
skipped tests in `server/internal/api/` encode it. See ADR-0004 for the rationale
and accepted trade-offs.

## 1. Principles

- The **client is the primary editor**; the server is the meeting point between
  devices. The app must work fully offline forever.
- **Decks and cards** are mutable state → synced with last-write-wins (LWW).
- **Review logs** are immutable facts ("at time T I graded card X as Good") →
  append-only upload, no conflict possible.
- Deletes are **tombstones**: `deleted = true`, never physical deletion.
- All `/v1` requests carry `Authorization: Bearer <token>` (static token until M3).

## 2. Data model (server, Postgres)

Written by the user in migration `0002` (issue M1-1). Columns every synced table
shares:

| column | type | meaning |
|---|---|---|
| `id` | `uuid` PK | the **sync id**, generated by whoever creates the row (client or server) |
| `user_id` | `uuid` FK → users | owner (the seeded system user until M3) |
| `updated_at` | `timestamptz` | last modification time, **set by the writer**; LWW comparator |
| `deleted` | `boolean` default false | tombstone |
| `server_seq` | `bigserial`, unique | monotonic sequence assigned by the server **on every write**; the pull cursor |

Domain columns mirror the Room entities:

- `decks(id, user_id, name, created_at, updated_at, deleted, server_seq)`
- `cards(id, deck_id, front, back, front_src, back_src, state, step_index,
  interval_days, ease_factor, repetitions, lapses, due_at, created_at,
  updated_at, deleted, server_seq)` — scheduling state syncs too, so a review
  done on one device reschedules the card on all devices.
- `review_logs(id, card_id, deck_id, reviewed_at, grade, state_before,
  interval_before_days, interval_after_days, server_seq)` — no `updated_at`, no
  `deleted`: immutable.

`server_seq` uses **one global sequence shared by all synced tables** so a single
cursor covers the whole pull stream.

## 3. Client-side metadata (Room, issue M2-1)

The Room entities keep their local `Long` PKs and gain:

- `syncId: String` (UUID, generated locally on create),
- `updatedAt: Long` (epoch millis, touched on every local edit),
- `dirty: Boolean` (true = has local changes not yet pushed),
- `deleted: Boolean` (soft delete; UI filters it out).

The pull cursor (`lastServerSeq`) is stored in DataStore.

## 4. Push — `POST /v1/sync/push`

```json
{
  "decks": [ { "id": "uuid", "name": "...", "createdAt": 0, "updatedAt": 0, "deleted": false } ],
  "cards": [ { "id": "uuid", "deckId": "uuid", "front": "...", "...": "...", "updatedAt": 0, "deleted": false } ]
}
```

Server behavior (issue M2-2):

1. Upsert by `id` (the sync UUID).
2. **LWW**: apply the incoming row only if `incoming.updated_at > stored.updated_at`
   (strictly greater — server wins ties). Rejected rows are not an error; they are
   listed in the response as `stale` so the client knows to pull.
3. Every applied write gets a fresh `server_seq`.
4. **Idempotent**: retrying the same batch must be safe (same `updated_at` → no-op).

Response:

```json
{ "applied": 12, "stale": ["uuid", "uuid"] }
```

## 5. Pull — `GET /v1/sync/pull?since={serverSeq}&limit={n}`

Returns all rows (decks, cards — including tombstones) with
`server_seq > since`, ordered by `server_seq`, up to `limit` (default 500), plus
the new cursor:

```json
{ "decks": [...], "cards": [...], "next": 1234, "hasMore": false }
```

The client applies rows with the same LWW rule against local `updatedAt`
(protects unsynced local edits), clears `dirty` only for rows it pushed, and
persists `next` as its cursor. Pull is repeated while `hasMore`.

## 6. Review upload — `POST /v1/sync/reviews`

```json
{ "reviews": [ { "id": "uuid", "cardId": "uuid", "reviewedAt": 0, "grade": 2, "...": "..." } ] }
```

Insert-only; duplicates by `id` are silently ignored (`ON CONFLICT DO NOTHING`).
**Think before implementing (issue M2-4): why can this endpoint never conflict,
while decks/cards need LWW?** The answer is the seed of milestone M5.

## 7. Sync session (client, issue M2-5)

```
push dirty rows → upload pending reviews → pull since cursor → apply → save cursor
```

Any step may fail; the session must be resumable (push and review upload are
idempotent; pull is read-only).

## 8. Known anomalies, accepted in v1

- Concurrent edits of the same card on two offline devices: the later
  `updated_at` wins, the other edit is silently lost (DDIA ch. 5's LWW warning —
  we accept it, single-user tool).
- Client clocks set the LWW timestamps; a device with a wildly wrong clock can
  clobber newer data. `server_seq` exists so *ordering of the stream* never
  depends on wall clocks. The spec tests include a clock-skew case to make this
  trade-off visible.
- No per-field merge: the row is the conflict unit.

v2 candidates (not now): version vectors per row, per-field LWW, CRDT text for
card content.
